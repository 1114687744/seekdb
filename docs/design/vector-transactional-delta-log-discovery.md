# 事务化向量 delta：用事务日志发现变化

状态：设计提案，尚未替换运行代码，也没有本方案的性能结果。
依据：独立 master 实验分支 `codex/vector-transactional-delta`，产品代码
`37a7bc65b`，空闲 CPU 实验归档 `cbd8cdfc6`。Namespace fork 分支不在本轮修改范围。

## 1. 要解决的具体问题

[空闲实测](vector-transactional-delta-idle-throughput.md)中，一个写过 10 万条且已追平的
异步索引，使原型持续消耗约 14.5%–15.4% 单核 CPU。原因是协调线程每 100 ms
重新扫描 delta，遍历仍在 memtable 中的历史键及删除版本。

目标同时包括：空闲时不扫描 delta；一个索引的写入不导致所有索引扫描；
前台事务不参与维护另一个共享待办名单；不为每个索引增加持久消费水位。

此前提出的逐索引变化/完成序号、全局变化序号、共享去重名单均不作为本提案方向。
它们需要额外的提交通知协议，或在活跃负载下引入无关扫描。

## 2. 职责与状态归属

```text
前台：主表 + delta 同事务提交
                 │
                 ▼
          已有事务日志
                 │ 后台独立读取
                 ▼
     一个协调线程：发现已提交的变化
                 │ 普通函数调用
                 ▼
       读取对应持久表的可见记录
                 │
                 ▼
      已有动态线程池：构图并等待本批结束
                 │
                 ▼
       原有转存事务：index_id + 删除 delta
```

日志用于定位需要检查的对象；主表、delta、index_id、snapshot 等持久表是恢复
向量状态的依据。不能把“delta 是可靠待办”误写为恢复只需要 delta。

协调线程私有：日志游标、尚未见到提交/回滚的事务及其涉及的物理对象、当前批次。
只保存对象标识，避免像旧 Fetcher 一样复制整份 redo 正文。
这些状态仍然存在，但前台和事务模块不修改它们；工作线程只更新本批任务完成状态。
不新增由前台、协调线程和工作线程共同维护的全局消费状态。

协调线程内采用同步的批次调用：取日志、形成批次、等待安全快照、构图、转存、
完成本批。当前批次失败就在本线程重试，不启动另一个独立推进的 Dispatcher。
工作线程仍使用原型已经验证的动态线程池及粒度。

## 4. 正常消费

1. 顺序读取新日志。redo 中只收集事务涉及的目标物理对象，去重发生在协调线程内部。
2. 看到事务提交后，将对象加入本轮局部批次；看到事务回滚就丢弃其目标。
3. 本轮多个已提交事务影响同一对象，可以合并检查。
4. 取得覆盖这些提交的可读快照 S。备库日志已收到，不代表事务已经回放可读；
   若尚未覆盖，等待并保留当前批次。
5. 向量模块通过所属上下文取得对应目录和辅助表，在 S 读取实际可见数据、构图。
6. 主库继续使用现有转存事务；备库只恢复本地向量状态，不修改复制表。
7. 成功后释放本轮局部批次；失败则重试，不以“日志已经读过”代表处理成功。

保存点回滚可以使对象集合多包含一个不再有可见变更的对象；MVCC 过滤其行，
最多产生额外检查。为发现对象无需重做旧 Worker 的逐行保存点可见性计算。
DDL、重建和对象删除需要刷新目录绑定；不能把任意映射未命中都当作对象已删除。

日志追平后仅检查日志尾部或等待已有日志机制；不调用全量 delta 消费轮次。
这里是减少空闲工作，不承诺整个数据库没有周期性唤醒或 CPU 消耗为零。

## 5. 日志游标能否只放内存

推荐的目标是：日志只加速发现工作，游标不作为新的持久可靠性水位，也不额外
阻止日志回收。但这需要明确的恢复协议，不能直接删掉旧 min_dep_lsn 使用点。

### 5.1 建立恢复与增量读取之间的衔接

1. **先**记住一个完整日志边界 L，作为随后增量读取的起点。
2. 再取得安全快照 S，确认 L 之前已提交的变更在 S 可读。
3. 在 S 核对持久辅助表，恢复当前需要服务的索引。
4. 从 L 开始消费后续日志；重叠部分允许重复检查。

不能先扫描表、再随手记录当前日志尾部：两者之间的提交可能既没被扫描看见，
又落在新的读取起点之前。

### 5.2 跨越起点的长事务

例如 T 在 L 之前写了 delta，在 L 之后才提交。S 的恢复扫描看不到未提交行；
从 L 读取可能只有提交或部分 redo，不能据不完整的对象集合宣布覆盖了 T。

读取器必须识别这种不完整事务。其提交可读后，执行一次持久状态核对，再继续
正常消费。即使已经看到 T 的一部分新 redo，仍可能遗漏 L 之前修改的其他对象，
不能只用“tx_id 存在”判断目标列表完整。

判定使用日志块序号、提交/redo 链等现有格式信息；这些字段的完整覆盖须在接入前
核实。此处描述的是设计要求，不是已经实现并验证的协议。

### 5.3 日志回收、重启和角色切换

游标指向的日志已回收时，重新执行上述衔接流程；运行期间不能静默跳到日志尾部。
重启、备库升主和本地向量状态重新建立也使用同一入口。
不把格式错误或日志损坏当成普通回收缺口直接跳过。

持久表恢复已经可用，仍需验证重复执行及部分成功后的幂等性。
日志持续落后并反复进入恢复会严重影响性能，需要可观测和测试；不能通过
“正确性最终可恢复”掩盖这种退化。

这项取舍把新持久消费水位及日志保留协调，换为启动、日志缺口或事务前缀不完整时
的持久状态核对。若这些核对在正常负载下频繁发生，本方案就没有达到目标。

## 6. Namespace fork、备库和 refresh

### Namespace fork

fork 创建子空间时，安排子空间索引的初始恢复。孩子继承的 delta、index_id、snapshot
按孩子的有效快照读取；不能等待不存在的“孩子写入日志”来发现继承的数据。
后续孩子自身的事务日志指向其物理对象。

目录与归属仍由上层显式提供。日志解析只认识物理对象，不新增 Namespace 专属日志
字段，不从全局变量或 TLS 推断归属。fork 生命周期接入属于后续 Namespace 集成，
不能由独立 master 原型的通过推断其已经完成。

### 备库

变化发现来自备库本地接收的日志，但执行依据回放后的安全可读快照。
需要覆盖主表及有关辅助表的变化，不能只通知 delta 插入。
本地日志游标由本地后台持有，不将主库的“构图已完成”当作备库完成证明。

### refresh

`refresh()` 请求一次覆盖指定提交边界的持久状态核对，并等待实际构图/转存完成。
这次显式操作允许检查其定义范围内的全部索引，从而不必靠全实例持续扫描来维护
一个永远前进的完成水位。失败或超时返回相应结果。
控制请求与工作线程同步仍然存在；它们封装在后台模块中，普通前台 DML 不参与。

## 7. 接口与改动范围

变化读取作为协调线程内部的同步模块，接口至少区分：有已提交批次、暂时无新日志、
需要恢复衔接、错误。接口不向前台暴露“登记待办/清除待办”，也不另设推送线程。
扫描及处理所需的目录、SQL 访问、事务快照、日志读取和向量运行对象显式注入。

| 保留/改造 | 具体内容 |
|---|---|
| 保留 | 主表 + delta 同事务；MVCC 可见性；原有向量持久辅助表 |
| 保留 | 已验证的构图动态线程池、批次粒度、构图后转存顺序 |
| 复用并收窄 | ChangeStream 的日志读取与事务格式解析，仅提取对象变化 |
| 替换 | `VectorDeltaConsumer` 的定时全量扫描，改为批次定向消费 |
| 实验路径删除 | 旧 Dispatcher 多批次游标、Worker 提交排序和跨模块撤销 epoch |
| 必须一并核实 | checkpoint 对 `change_stream_min_dep_lsn` 的依赖及旧监控口径 |
| 改造 | 主动 refresh、恢复衔接、备库读取边界 |

当前原型已经关闭旧 Fetcher，但 checkpoint 仍读取旧 min_dep_lsn；因此“数据已移到
持久 delta”并不等于日志回收的依赖已经拆干净。本轮只定位到代码关系，未通过
长时间磁盘占用试验证明实际保留量，不能声称日志回收问题已经修复。

## 8. 接入门槛与验证

先证明变化读取覆盖以下情况，再替换二进制：事务前缀截断、长事务跨起点、
合并日志块/分段日志、辅助表维护日志、目录变更、日志被回收后的衔接。
确认后仅运行与改动直接相关的短用例及性能实验，不跑完整 mysqltest/sysbench。

性能复用现有脚本和资源配置：

- 无索引、空索引、写过 10 万条并追平后的真正空闲 CPU。
- 单客户端不限速提交吞吐，以及后台追平时间。
- 持续写入时的新数据可查询延迟、查询 P99 和召回率。
- 多索引中仅一个索引有写入，检查无关索引是否被扫描。
- 重点统计日志读取/解析 CPU、持久表检查次数、发生恢复衔接的次数。

设计评价以新增状态的所有者、生命周期、异常恢复路径和实测成本为依据。
复用 ChangeStream 的名字本身不构成更简单或更高性能的证据。

# 物理布局随本地数据保存：收敛方案

日期：2026-10-12。

状态：架构提案，尚未实现、未获得动态验证。用于替代讨论中反复变化的“只给 SSTable 加描述，再考虑来源和 GC”的方案；不修改已完成实现的验收结论。

最新长期目标见第 12 节：统一权威目录、事务发布与历史读取，让 SQL 和后台维护都消费目录；物理对象保存自己所需的完整描述。第 1—11 节保留布局历史及补充校验元数据的讨论是现有架构下的过渡候选，不应在长期目标中继续增加独立的派生历史。此处区分目标架构与近期改造，未宣称现有实现已具备统一目录模块。

## 当前架构建议：合并与逻辑校验均不依赖 Namespace 服务启动

不能把当前 checksum 会启动 Namespace 当作不可改变的条件，再据此让物理合并也依赖完整 SQL 服务。当前 `ObMajorMergeProgressChecker::check_progress()` 经 `prepare_namespace_login()` 取得所属 SQL proxy 和 SchemaService，主要为了读取历史定义和判定 DDL 替换；数值比较本身不要求 SQL 执行环境。

目标建议是让合并准备和逻辑校验都按需消费已经提交的持久元数据，不经过 Namespace 服务启用入口。逻辑校验仍知道 Namespace 归属、主表/索引关系；物理合并只接收物理对象和完整输出描述。元数据归属与服务启动依赖是不同问题，不能把两者混同。

第 1—10 节保留布局历史表的路线仍是物理描述方案的候选。表的去留由元数据权威来源、快照保留与重复发布的总成本决定，不以少一张表为优先目标，也不因当前 checksum 的实现就认定 SQL 服务依赖必须保留。第 11 节记录解除这项依赖的源码依据及需要补齐的内容。尚未实施代码改造或动态验证。

## 1. 选择

采用以下完整链路：

1. 上层在创建 tablet 或首次以新布局写入时，交付完整物理描述。
2. 存储先把描述安装为该 tablet 的持久元数据，再接受需要该布局的新写入。
3. 转储从本地已安装的完整描述取得输出布局；任务取得不可变正文的有效持有者。
4. SSTable 保存实际输出布局的完整正文。
5. 文件读取、复制、fork 重写从文件自己取得描述。
6. 大合并仍按目标 SCN F 从 DDL 发布历史选择输出布局，并固定在任务中。

为消除转储对外部历史正文的依赖，明确接受“首次使用新布局时安装一次本地元数据”的成本。这个选择不是因为普通行回放需要完整 schema；当前普通行回放不需要。它服务于转储、重启后的转储以及备库独立转储。

### 1.1 各份描述的分工

| 位置 | 保存的内容 | 何时变化 | 负责什么 |
| --- | --- | --- | --- |
| Namespace 的 SQL schema | 表的逻辑定义 | DDL 提交 | SQL 解析、执行和逻辑可见性 |
| DDL 物理布局历史 | 各次已发布的完整物理描述 | 与 DDL 同事务发布 | 按合并目标 SCN F 选择输出布局 |
| tablet 已安装写入布局 | 本 tablet 已接受的完整写入描述 | 创建或首次使用更高布局版本写入 | 未转储数据后续生成文件，包括崩溃恢复后的转储 |
| 合并任务/medium 信息 | 本次输出采用的完整描述 | 准备任务时固定 | 执行期间不随并发 DDL 改变 |
| 每个 SSTable 的元数据 | 该文件实际采用的完整描述 | 创建文件时确定 | 解释、复制和重写该文件 |

文中的 V 是完整描述对应的 schema 版本，不是 SCN。G 是已有的物理布局身份，用于区分布局演进链；它不是 Namespace ID，也不是版本大小。不能把父子分支不同 G 的 V 直接比较。

两条数据流：

```text
SQL 所用表定义 → 完整写入描述 → tablet 安装并持久化 → mini → SSTable 自带描述
DDL 同事务发布 → 物理布局历史 → 按 F 选择完整描述 → medium/major → SSTable 自带描述
```

前一条负责本地数据可转储，后一条负责历史目标正确。完成历史合并不能回退 tablet 的写入布局。

## 2. tablet 描述的唯一职责

定义为：**该物理 tablet 已安装的、可以用于继续接收写入和生成文件的完整物理布局。**

- 它不承诺等于 SQL 目录的最新定义。
- 一个从未使用新布局写入的 tablet 可以继续持有旧布局。
- 它不代表所有输入文件的布局；文件各自持有自己的描述。
- 它不负责按 SCN 查询逻辑历史；大合并的目标布局另由 DDL 历史提供。
- 同一物理布局演进链上，只允许安装能够兼容该 tablet 现存增量数据的布局。版本号比较只能判断先后，不能代替兼容性。
- 当前值只由创建/布局安装入口更新。mini、major、meta 和文件接管不能通过取列数最大值、提升版本号或安装旧轮次文件反向修改它。

完整正文的版本必须来自该正文，禁止旧正文换新版本号，禁止省略列信息后仍作为完整描述使用。

## 3. 使用现有 MDS 持久化当前值

新增一个 tablet MDS 当前值类型（建议名称 `TabletWriteLayout`），使用固定 key，保存完整物理描述并绑定布局身份 G。V 取自正文已有的 `ObStorageSchema::schema_version_`，不再维护另一个可独立变化的版本字段。按“保留未提交值与最新已提交值”的用途接入，不建设每 tablet 的应用级完整历史列表。

MDS 是已有的 tablet 元数据事务、回放、转储与检查点框架：

- `mds_register.h` 的 `NEED_MULTI_VERSION=false` 明确对应未提交值和最新已提交值。
- `ObMdsTableMgr::init()` 已向事务服务注册 MDS checkpoint。
- MDS 内存节点释放与落盘读取已有框架，新增变长描述仍须接入内存计量和序列化。

实现需要增加 MDS 数据类型和事务日志分派/回放接入。调用一次 `set()` 并不自动完成全部工作，不能把这项接入描述为零成本。

现有 `storage_schema_addr_` 的用途逐项迁到这个唯一来源或 SSTable 自带描述，最终移除这份独立正文。允许活跃任务持有正文、活跃写入持有当前描述；不保留两个独立推进的持久权威，不建立全实例描述缓存或永久版本字典。

这里确实产生描述的日志字节，复用现有 MDS/事务日志，不设计独立描述 WAL 或在每条行日志重复正文。日志回收由元数据检查点约束。

## 4. 创建与写入协议

### 4.1 创建

创建 tablet 时已有完整 `ObCreateTabletSchema`。创建事务同时建立初始安装布局。普通创建、fork 物化、隐藏表创建通过共同入口完成；固定内部元数据对象使用引擎既有固定描述，避免依赖用户目录。

fork 的初始布局来自上层已固定的 fork 目录定义。存储收到物理对象和完整描述，不解析 Namespace。

### 4.2 首次使用新布局

“首次”通过本次写入要求的布局与 tablet 已安装布局比较得出，不设第一次写入标志，不扫描其他 tablet。

当前 `ObDMLRunningCtx::init()` 已将 `dml_param_.schema_version_` 传入 `store_ctx_.table_version_`。它是本次执行采用的版本；当前参数尚不等于完整的 `ObStorageSchema`，本方案需要补齐正文交付和安装入口。

| 本次写入要求 | tablet 已安装 | 动作 |
| --- | --- | --- |
| V11 | V10 | 安装完整 V11，提交后接受依赖它的写入 |
| V11 | V11 | 复用已安装描述，普通写入 |
| V10 | V11 | 在既有 DDL 协议允许且布局兼容的条件下写入，不降级 |
| V13 | V10，中间没有以 V11/V12 写入 | 允许直接安装兼容的完整 V13，不补装未使用的中间版本 |

以上比较限于同一物理对象允许的布局演进链；不能用版本数字代替布局兼容性检查。

1. SQL 上层从本次执行采用的 `ObTableSchema` 构造完整物理描述。复用现有 `ObStorageSchema::init()`，由执行上下文持有，不逐行构造，不复制分区数组。不能把旧执行版本配上临时查询到的最新正文。
2. 写入准备入口检查 tablet 当前安装布局。
3. 已安装兼容布局时取得持有者，进入普通写入；不逐行读 MDS，不逐行复制正文。
4. 需要更高版本时，在同一 tablet 上串行完成一次布局安装元数据事务。并发写入共享其完成结果。
5. 安装提交、描述成为可恢复状态之后，才允许需要新布局的数据进入写入链路。

例如两个 V11 请求同时看到本地 V10，串行入口内必须重新检查：第一个完成 V11 安装后，第二个复用结果，不重复提交。安装失败则本次依赖它的写入失败或按既有重试规则处理，不能先写数据后补描述。

安装使用已经提交的 DDL 定义，不是再次发布 DDL。数据事务后续回滚也无需撤销这个已合法发布的物理布局。

布局安装事务不取得 SQL DDL 锁，不反查 SchemaService；上层负责交付合法、完整的描述。tablet 删除/替换仍受物理 incarnation 和现有生命周期协议限制，不能向已经退休的对象安装布局。

### 4.3 并发旧写入

新布局兼容同一物理对象既有布局，是安装前置条件。已在执行的旧布局写入只要仍被已有 DDL 协议允许，就可继续写入；安装版本不得倒退。完整新布局必须覆盖它们的物理列位置、编码与缺列语义。

不能就地兼容的变更，沿用数据重建/物理对象切换协议。普通在线 DDL 继续在线，不通过强制每次 DDL 转储或切换 MemTable 解决。

这项约束须集中验证。当前 instant drop 保留 unused columns，能够提供重要基础；它不等于已经证明所有 DDL 都兼容。实施验收必须覆盖类型变化、生成列、列重建和分区切换，不能只测 ADD COLUMN。

## 5. 转储与文件合并

### 5.1 mini

- MemTable 的版本、列数统计继续存在，用来验证当前完整布局覆盖本次输入。
- 任务从本地已安装布局取得完整不可变描述，并在任务期间持有正文。
- 回放尚未安装所需布局时，任务等待该元数据回放完成。不能退回查全局历史，也不能生成简化描述继续执行。
- mini 保持现有 MVCC 行与 NOP 语义，不因描述完整就填默认值、改变可见性或变成 major。
- 创建 SSTable 时，数据与实际输出描述一起进入既有文件元数据持久化和安装流程。

### 5.2 minor / meta

输入的每个文件使用自己的描述。输出从本地已安装描述与输入文件的完整描述中，选择本物理对象兼容演进链上覆盖本次输入的完整布局，准备阶段固定，执行期间不再修改。相同 G 和更大的 V 本身不能代替兼容性检查。

必须覆盖“DDL 后无 DML，major 已使用新布局生成文件，但写入布局还没升级”的情况：meta 可以取得该输入 major 自带的新布局，不能强行用较旧的本地写入描述覆盖它，也不需要为此反向升级已安装写入状态。

跨 fork 来源不能比较不同 G 的 V 并取最大值。必须先按已有 fork 快照上界和目标列绑定解释输入，确保父分支在 fork 后引入的列和值不进入孩子。实际重写输出按目标布局生成；原样复用的文件保留其原描述。

父子分别增加同位置不同类型的列、宽父文件与窄孩子增量混合，是必须通过的行为测试。不能用“列数足够”替代这项校验。

### 5.3 major / medium

目标 SCN 对应的输出布局仍从 DDL 发布历史获得，固定到已有 medium 信息。已安装写入布局可能更晚，不覆盖历史目标。

完成旧轮次合并只安装携带旧目标描述的新文件，不回退 tablet 的已安装写入布局。

## 6. 恢复、检查点与备库

| 崩溃位置 | 恢复要求 |
| --- | --- |
| 新布局安装提交前 | 需要它的新数据尚未被接受，无未保护数据 |
| 安装提交后，尚无数据写入 | 恢复一份暂未使用的新布局，合法且无须回滚 |
| 数据已有日志，布局元数据尚未转储 | MDS 检查点必须保留描述日志，回放恢复它 |
| 布局已转储，相关日志已回收 | 从 tablet 的持久 MDS 当前值恢复布局 |
| 文件与元数据已写出，尚未原子安装 | 沿既有文件/元数据安装协议处理；不能仅因临时文件存在就推进保护 |
| 新文件已安装 | 文件自己携带完整描述，脱离外部历史正文 |

元数据安装与新数据存在主库提交先后关系。备库可能并行处理回放，普通行恢复仍可先完成；本地转储必须验证所需已安装布局可见，尚未到达时等待依赖。

主备使用各自的元数据检查点和文件安装进度，主库不能依据自己的转储进度删除备库尚需的描述。此处通过复制的 MDS 更新和各副本原生检查点解决，不发“根据主库本地文件引用生成的历史正文 DELETE”。

待验证的实现细节是新增类型到既有检查点的正确接入，不另起一套持久 pin、恢复队列或副本确认水位。

## 7. 历史表与回收

DDL 物理布局历史继续解决“F 时刻应该使用哪个布局”。它只服务逻辑时刻选择：

- DDL 与 SQL 目录同事务发布完整布局。
- 使用按 G（必要时加分块号）组织的普通 MVCC 正文；同 key 更新形成历史。
- 删除逻辑对象时同事务删除当前记录；旧快照仍由 MVCC 保留。
- 保留边界继续由既有未完成 freeze、持久合并进度和活跃历史读者确定。
- 读者在结束历史读取保护之前，将完整正文固定到任务自有对象/持久 medium 信息。

已经安装的本地写入布局、MemTable 的后续转储和 SSTable 不再向这张表申请长期保留。

因此目标删除：

1. 以 `(G,V,chunk)` 独立不可变行长期保存正文的专用回收方式。
2. `StorageSchemaHistory::collect_physical_references()`。
3. 专为布局 GC 设置的 `scan_tablet_references()` 全实例旧对象/文件扫描及发布变化补扫。
4. `StorageSchemaHistoryFilter` 专用正文删除过滤器。
5. mini 的 `column_info_simplified` 生成和后续补全文字典查询。

这些代码只有在所有物理消费者切换后才能删除。其他用途的对象生命周期管理、数据文件引用和目录页 GC 不在删除范围内。

分块正文缩短时，必须在同一 DDL 事务处理旧尾块，历史快照通过 MVCC 读取完整旧版本；不能留下版本混拼。

## 8. 代价

- 每个实际采用新布局写入的 tablet，每个安装版本产生一次完整描述的元数据持久化成本；首次写入会等待安装完成。
- 8000 个分区全部开始写新布局，最终仍会发生 8000 次本地安装。避免的是 DDL 提交时的集中下发与复制，不能宣称消除了线性总量。
- 每个 SSTable 一份完整描述，增加磁盘、元数据缓存及载入成本。
- 只读且未使用新布局的 tablet 不因 SQL 目录更新而自动安装新布局。
- 不按内容去重，不引入共享持久正文池；活跃执行可以持有不可变对象引用，需纳入原有内存预算。
- 不承诺新增成本很小；性能验收需要覆盖宽表、小事务、频繁 DDL 和 8000 分区，而不是只跑窄表大批量写入。

收益是移除物理对象对外部历史正文的生命周期依赖，让复杂度集中在一个布局安装入口与既有持久化基建中。

## 9. 实施验收

先验证完整链路，再删除旧机制，不运行完整 mysqltest/sysbench：

1. V10 数据未转储，在线 DDL 到 V11，再写入；强杀后回放、转储、读回及文件描述核对。
2. 布局安装事务提交/回滚、失败重试、多线程首次安装、旧写入并发；安装版本与正文始终一致。
3. DDL 后无数据、安装后无数据、元数据已转储但数据未转储等窗口，推进日志回收后强杀。
4. 一个 MemTable 跨多次在线加删列、默认值修改和兼容类型修改；保持原 MVCC/NOP 语义。
5. 不兼容 DDL 通过重建/物理对象切换，不在同一对象中混装不能互相解释的布局。
6. fork 父子分别修改列、来源跨 G、宽窄布局联合 minor/meta、父删除、两次重启。
7. F 发布后 DDL，旧 F major 仍用旧目标，完成后本地写入布局不回退。
8. 备库布局与行日志并行回放、不同转储/日志回收进度、完整复制、强杀与提升。
9. 彻底禁用旧物理引用扫描与正文过滤器，再运行历史版本回收和上述行为测试。
10. 8000 分区及宽表首次安装、普通写入稳定态的延迟、内存、日志量；记录新增成本。

此前出现过失败的相关用例继续进入四件套。本提案没有运行这些验证，不把设计论证当作已有测试结果。

## 10. 实施顺序与完成标准

1. 先贯通一个 tablet 的完整链路：上层交付完整描述、安装事务、日志回放、MDS 检查点和重启恢复。以新旧布局写入并发和强杀窗口验证安装协议。
2. 让 mini 和新建 SSTable 使用完整描述；把读取、minor/meta、fork 重写、复制恢复等物理消费者迁到文件或本地安装描述。所有文件生成入口都必须有明确来源。
3. 保留 major 按 F 取历史布局的职责，将历史正文改为普通 MVCC 更新；物理消费者不再依赖历史正文后，删除专用引用扫描、变化补扫、正文过滤器和简化描述生成。
4. 执行第 9 节针对性验证，记录日志量、内存和首次写入成本；相关用例纳入四件套。

完成标准是“未转储数据有可恢复的本地描述，已生成文件有自带描述，历史查询只受逻辑快照保留约束”。这不是只增加 SSTable 字段便完成的局部修改。当前阶段仅确定设计，未实施上述代码改造。

## 11. 逻辑 checksum 脱离完整 Namespace 服务

### 11.1 当前真正消费的信息

`ObTableCkmItems` 的数值比较不访问 SchemaService 或 SQL；目前传入 `ObTableSchema` 是为了取得以下数据：

- 主表/索引归属、索引类型及可读/适用状态。
- 逻辑列 ID 与 checksum 数组位置的对应关系，隐藏列、shadow 列、非存储列的比较规则。
- 目标 F 下的完整预期 tablet 集合、local 索引分区配对、global 索引聚合范围。
- FTS 等现有特殊类型的辅助表配对规则。
- 物理对象 incarnation、目标 F、产生结果的布局/定义版本，用于校验结果身份。

`ObChecksumValidator::load_definition()` 和 `check_retirement()` 才通过所属目录 SQL/SchemaService 取定义及 DDL 替换证据。后者也必须切换到已提交元数据，不能只替换正常比较路径。

错误记录入口虽然接收 `ObISQLClient &`，当前 `ObColumnChecksumErrorOperator::insert_column_checksum_err_info()` 实际忽略该参数，调用已有本机 SQLite 存储。应移除这个无用依赖，无须因此新建错误存储。

### 11.2 建议的模块职责

DDL 统一发布入口从完整表定义提取校验所需关系与列映射，与目录和布局同事务发布。后台元数据读取模块按 F 取得这些事实，形成一次校验使用的临时输入；比较模块消费输入与物理 checksum。禁止从已经到达的 checksum 反推完整预期集合，也不能因缺项而静默缩小校验范围。

已有 `TableCreationDescriptor` 保存完整物理描述和部分主表/辅助表关系，已有目录 source tree 保存逻辑 tablet 到表、物理 incarnation 的绑定。优先核对复用与补齐这些已有发布数据，避免再建立一份完整 `ObTableSchema` 或第三套分区清单。当前内容尚不够替代校验输入：逻辑列映射、部分索引/辅助表关系及分区配对仍须补齐。

这不是新增一个常驻 Namespace runtime。读取使用已有原生元数据事务与按需解码；一次工作结束释放临时输入。逻辑校验元数据留在上层，不能塞进存储层 `ObStorageSchema` 后让物理存储理解 Namespace 或主表/索引语义。

### 11.3 必须闭合的代价与正确性

这项改变增加 DDL 发布元数据及其维护责任。提取必须集中在统一定义发布入口，索引状态、列映射和分区绑定变化都要覆盖，不能让每种 DDL 手工决定是否通知校验。8000 分区下，表级属性与 tablet 绑定分开组织；普通列定义修改不应重新持久化全部分区绑定。

若复用 COW 目录，F 的目录根、源绑定及描述对象必须在整个需要期间可读，且重启后仍受持久未完成 freeze 保护。当前布局表的保留不能被当作已经保护了通用 InstanceMetaStore 的目录页；需要分别核对 MVCC 与目录页 GC 的接线。若保留普通 MVCC 布局表，也必须为校验关系提供同一 F 的一致视图，不能混用最新关系和历史布局。

验收应在参与校验的 Namespace 服务保持未启用的条件下覆盖完整轮次、重启和错误上报；覆盖 local/global 索引、现有 FTS 配对、fork 同名对象、F 前后 DDL 和相同数量分区替换，证明缺失输入仍阻止成功、不一致仍报错。这些是目标验收条件，不是当前已有测试结果。

## 12. 长期目标：统一权威目录，而非逐消费者增加历史副本

### 12.1 问题与边界

schema 参与 SQL、写入和合并是关系数据库的正常需要。当前问题在于定义权威、缓存、版本选择、物理对象描述和回收职责混在一起：完整定义通过 SQL 读取，部分物理路径仅保留版本/列数再补全，后台为少量定义启用完整 Namespace 服务，多种派生持久描述又各自需要发布和保留。

目标中的目录（Catalog）具体指表、列、索引关系和逻辑到物理绑定的持久定义，以及管理其事务和快照读取的模块。它位于 SQL 运行时之下，使用原生元数据读写；Namespace 归属由显式目录身份/分支根表达，不要求启动 Namespace 的 SQL、计划缓存或其他服务。不能仅包装一个仍调用 Namespace SQL 的 `get_schema()` 就声称完成。

### 12.2 一份权威，按事务快照取得完整定义

- DDL 通过目录写接口提交完整、已验证的对象变更；同事务涉及的主表、索引与绑定一起可见。
- 定义版本是不可变身份，提交 SCN 决定何时可见；不同 Namespace 的版本号不用于比较提交先后。
- 目录统一提供按对象/按目标快照的读取、实际需要的枚举及历史保护；消费者不自行选择最新版本、拼凑表列版本或取 MIN 掩盖缺失。
- 权威数据通过已有原生事务、日志、回放、MVCC 持久化。内存服务和缓存失效后可从这份数据重建。
- 元数据存储自身使用引擎内建固定格式，读取目录不以先启动完整 SQL/schema 服务为前提。

这是一套逻辑模型与发布协议，不要求把全部内容序列化成一个大 blob。表/列定义、索引对象、分区与物理绑定应按变更和访问粒度组织：普通列变更不重写 8000 个绑定；单 tablet 的写入准备不读取整表分区清单。

### 12.3 SQL 和后台是目录的消费者

SQL 侧的 SchemaService 保留运行时对象、访问 guard 与缓存等适合它的职责，其定义来源下沉到目录模块。合并准备和 checksum 也从同一目录模块读取，不经 SQL 服务激活。

同一不可变定义按用途产生临时视图：

- SQL 使用名称、逻辑列、约束、索引等定义。
- 物理描述构造器产生完整 `ObStorageSchema`，转换规则集中维护。
- 校验准备读取同一 F 的主表/索引、列映射、状态及完整绑定，生成本次比较输入。

校验输入不再拥有独立的持久历史表。表和索引的分区可能不同、状态和定义版本也不同，必须依靠同一 F 的完整对象集合确定关系，不把一个主表版本当作全目录版本。

物理合并继续只消费已解析的物理对象、F 和完整输出描述。目录归属与物理对象到定义的绑定由目录/上层维护模块解释，不分散到存储任务中。逻辑 checksum 位于目录上层，仍保留 Namespace 隔离，不能为省去 Namespace runtime 而取消逻辑归属。

### 12.4 数据流与物理描述所有权

```text
DDL → 目录事务提交
          ├─ SQL SchemaService/执行：按需取得定义
          ├─ 写入准备：构造完整描述 → tablet 持久安装 → 数据写入
          ├─ 合并准备：按 F 构造完整描述 → medium 信息 → 文件合并
          └─ 校验准备：按 F 取得关系、列映射、绑定 → checksum 比较

tablet 的已安装描述 → mini 输出描述 → SSTable 自带完整描述
```

SQL 当前定义、tablet 已安装布局、旧文件描述可以属于不同版本，分别有明确职责。物理副本是数据对象使用的不可变描述，不可自行补列数后冒充新版本，也不参与重新发布逻辑 schema。

历史保留分成两个明确协议：目录历史按尚需读取的逻辑快照保留；tablet/任务/文件的本地描述由持有对象负责。文件可能比目录历史保留得更久，文件自带描述使其无需请求目录保留旧正文。两种寿命不能重新混入全实例物理引用扫描。

### 12.5 对现有表与改造范围的含义

达到上述目标后，单独的物理布局历史是可替代的派生副本：合并需要的布局可由权威目录历史构造；独立 checksum 历史也不需要。布局/校验所需的全部元数据必须先纳入目录定义，目录必须先有精确 F 读取及可靠保留，才能删除旧来源。

`__all_table`、`__all_column` 等兼容 SQL 查询入口可以展示权威目录，不再与另一份原生目录各自维护定义。具体物理组织需要单独设计，不能让原有 SQL 内表与新 KV 长期双写后仍称为“一份权威”。其他非 schema 系统表不包含在此次目录定义中。

这属于 schema 子系统重构，涉及 DDL 写接口、SQL schema 装载、历史查询、fork 目录绑定和后台准备，不是给 checksum 新增一张 KV 表的局部修改。近期物理描述自包含的工作可独立推进；若只做近期改造，应明确把布局历史表保留为过渡来源，而非先删掉再通过 Namespace SQL 回退补齐。

### 12.6 与现有 SchemaService 和非表对象的关系

权威目录覆盖原有 schema 定义，包括 database、table、column、index 以及其他适用的 schema 对象，并非只保存合并所需字段。对象类型、Namespace 归属和访问粒度彼此分开：请求一张表不要求装载所有 database、用户或其他表；对象的具体归属继续遵守已有作用域设计。

建议从现有后端边界拆分：`ObMultiVersionSchemaService::init()` 已接收 `ObSchemaService &schema_backend`，其上层 guard、名称/ID 查询、schema 对象缓存和刷新可保留；后端持久化与历史读取改由独立目录模块提供。当前后端接口仍混入 `ObISQLClient` 和 SQL 装载语义，需要调整，不能认为只替换一个实现就能完成。DDL 的持久定义写入也必须同步收敛，不能只改读路径而留下两份写权威。

表名、注释、所属 database 等完整逻辑属性由权威表定义保存，SQL 的 `ObTableSchema` 继续包含它们。上层统一构造器从同一版本定义生成存储所需的完整 `ObStorageSchema`，不携带表名、注释或 database 对象；checksum 提取其所需的逻辑映射。合并需要的列类型、排序规则和默认值等应使用已经确定的有效值，不能临时沿 database/会话属性链求解。

统一是一个持久定义来源和事务/快照协议，不是一个巨大的通用 schema 结构，也不要求把每个字段拆成单独 KV 记录。先按实际访问粒度组织：表基本信息、列定义与大规模分区/物理绑定分离；少量表名等字段可随表级记录按需解码后不进入物理描述，无须为节省几个字符串另造一份长期维护的存储专用表定义。后台只构造所需视图，不必创建 SQL 侧完整 `ObTableSchema` 及分区数组。

database 等非表对象通过同一个目录事务和历史读取基础保存、由 SQL SchemaService 按需装载，不为它们生成物理布局，不进入 tablet/SSTable。SQL 系统表查询入口展示相同权威数据；将现有 SQL 实现迁到原生目录后，不为后台再保留一套 database/table 定义副本。
